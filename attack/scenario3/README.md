# scenario3 — OS 커맨드 인젝션 → 호스트 셸 → 지속성 → 파일 변형

AWS API 를 한 번도 부르지 않는 시나리오. **호스트 안에서만** 움직인다.
scenario1 이 클라우드 랜섬(S3 객체)이라면 이쪽은 전통적인 호스트 랜섬이다.

## ⚠️ 사전 조건 — 대상 파일이 미리 있어야 한다

`/opt/whs-lab-data/` 에 파일이 없으면 4단계가 `NO_TARGETS` 로 중단한다.
**공격 스크립트는 잠글 대상을 직접 만들지 않는다** — 그러면 "원래 있던 데이터를
암호화했다"가 성립하지 않기 때문이다.

인프라 쪽(Golden AMI 또는 시작 템플릿 user_data)에서 심어 둔다.
수동으로 심으면 인스턴스 격리·교체 시 사라진다.

```bash
mkdir -p /opt/whs-lab-data
# ... 더미 파일 생성 ...
chown -R ec2-user:ec2-user /opt/whs-lab-data
```

**`chown` 이 핵심이다.** `/opt` 는 root 소유이고 웹앱은 `ec2-user` 로 돈다.
소유권을 안 넘기면 `.bak` / `.locked` / `restore.sh` 를 쓰지 못하는데,
목록 조회는 되고 쓰기만 실패해서 원인을 찾기 어렵다.

**공격** — 웹앱 로그인 계정, `SSH_PROBE_TARGET`(**반대쪽** 인스턴스 private IP).
비워두면 `127.0.0.1` 로 가는데 루프백이라 ENI 를 안 타서 Flow Log 에 아무것도 안 남고,
로컬 sshd 가 응답해 `SSH_OPEN` 이 나온다 — 이 단계의 의도와 정반대 결과다.

**복구** — `UPLOAD_BUCKET`, `RESTORE_AWS_*` (`s3:DeleteObject`).
호스트 복구에는 AWS 자격증명이 필요 없고, S3 에 올린 `impact.sh` 를 지울 때만 쓴다.

## 실행

```bash
python scenario3.py             # 1~4 전부
python scenario3.py --restore   # 전부 되돌림
```

`--restore` 가 되돌리는 것:

```
1) 4단계 변형       restore.sh 실행 → .locked 복호, 원본 복원
2) 잔여물 제거      .bak / restore.sh / NOTE.txt
3) 3단계 마커       ~/.bashrc 에서 삭제
4) S3 impact.sh     운영자 자격증명으로 삭제
```

2번은 **`.locked` 가 하나도 안 남았을 때만** 실행된다. 복호가 덜 끝났는데 `.bak` 까지
지우면 원본이 영구히 사라지기 때문이다. 남아 있으면 `.bak` 을 보존한 채 중단하고
수동 복구 명령을 띄운다. 실제로 `restore.sh` 가 없어진 상태에서 정리만 돌아
더미 3개를 날린 적이 있다.

대상 호스트는 `recovery/impact_manifest.json` 의 `target_host` 에서 읽고, 없으면
`persistence_marker.json` 으로 폴백한다. 새로 고정하지 않는 이유는 ALB 가 다른
인스턴스를 주면 공격한 곳이 아닌 데서 복구하게 되기 때문이다.

되돌리지 않은 흔적이 있으면 **다음 실행이 막힌다.** 그대로 또 돌리면 ALB 가 다른
인스턴스를 줄 수 있고, 그러면 기록된 `target_host` 가 덮어써져 먼저 심은 쪽을
`--restore` 로 찾지 못한다.

ASG 가 인스턴스를 교체하면 호스트 흔적은 알아서 사라진다. 그 경우 `--restore` 는
대상 호스트가 없어 실패하는데, 버그가 아니라 **격리가 작동한 결과**다.

## 알아둘 것

**4단계는 실제 암호화가 아니다.** base64 인코딩이라 키 없이 `base64 -d` 로 되돌아가고,
원본은 `.bak` 으로 남으며 `restore.sh` 를 변형 **전에** 만들어 둔다.

그래서 EDR·ELK 의 엔트로피 기반 랜섬웨어 룰에는 걸리지 않을 수 있다. 암호화된 파일은
엔트로피가 8.0 에 가깝지만 base64 는 6.0 정도다. 탐지 룰을 검증하려면 실제 대칭키
암호화로 바꿔야 한다(가역성은 키를 `recovery/` 에 저장하면 유지된다).

**호스트에는 잠글 가치가 있는 데이터가 거의 없다.** 앱 소스는 git 에 있고, 업로드
파일과 고객 데이터는 S3·RDS 에 있다. stateless 한 구조라 호스트 랜섬의 실익이 없다는
뜻이고, 이건 약점이 아니라 아키텍처가 잘 된 결과다. 실제 공격자라면 scenario1 쪽으로 간다.

**명령 길이 제한이 빡빡하다.** `/api/labs/os-command` 는 200자 제한인데 대상 고정
가드가 77자를 먹는다. 3단계 마커를 32자 넘게 잡으면 한도를 넘어 중단된다(기본 26자).
긴 스크립트는 업로드→실행 경로로 보낸다.
